Events
======

:doc:`02_build_and_simulate` built a model with a fixed rate law and
simulated it straight through. Real kinetic models often need to change
mid-run — a parameter switches at a fixed time, a feed pulse hits a
reactor, a control action fires when a species crosses a threshold. This
page covers :class:`~nskinetics.Event`, the low-level building block for
all of that. :doc:`04_fed_batch_feeding` builds on it with
:class:`~nskinetics.FeedSpike`, a higher-level convenience for fed-batch
spikes.

Declaring an event
-------------------

:class:`~nskinetics.Event` mirrors a native SBML event: a trigger
expression (``when``) paired with one or more variable assignments
(``do``) that fire once the trigger becomes true. Every variable named in
``do`` must be a **non-constant** model variable. Here is a minimal model —
species ``s`` decays at rate ``k`` while a ``flag`` parameter is nonzero —
with an event that flips ``flag`` off at ``time >= 5``:

.. code-block:: python

   import tellurium as te, nskinetics as nsk

   model = """
   model decay()
     species s; s = 100; k = 1; flag = 1;
     s' = -k*flag*s;
   end
   """
   r = te.loadAntimonyModel(model)
   km = nsk.KineticModel(r, units={'time': 'h', 'conc': 'g/L'})
   km.add_event(nsk.Event(when='time >= 5', do={'flag': '0'}, name='stop_decay'))

:meth:`~nskinetics.KineticModel.add_event` only appends the
event to a pending list (``km.events``) — it is not yet part of the
model. Call it as many times as needed to queue up several events before
compiling them together.

Compiling events — and the lifecycle gotcha
----------------------------------------------

.. warning::

   Compiling events **regenerates the underlying RoadRunner model** and, as
   a side effect, **resets all model state to its SBML-defined origin
   values**. Any custom initial conditions or parameter overrides must
   therefore be set **after** calling ``compile_events()``, never before —
   values set beforehand are silently discarded when the model is
   regenerated. This is documented directly on
   :meth:`~nskinetics.KineticModel.compile_events`,
   :meth:`~nskinetics.Event.compile`, and
   :meth:`~nskinetics.FeedSpike.compile`. The safe ordering is always:
   ``add_event(...)`` (repeatable) → ``compile_events()`` → set any custom
   ICs/parameters → ``reset()`` → simulate.

:meth:`~nskinetics.KineticModel.compile_events` injects every
pending event into the model and regenerates it once (it is guarded, so
calling it again after it has already succeeded is a no-op). Follow it with
:meth:`~nskinetics.KineticModel.reset`, which restores model
*state* — species amounts, time — to the (now regenerated) origin values,
without touching structure:

.. code-block:: python

   km.compile_events()   # regenerates the model; set ICs AFTER this
   km.reset()

Because this example sets no custom ICs, ``reset()`` here simply guarantees
a clean start from the Antimony-declared values (``s = 100``, ``flag = 1``).
If you did need a custom starting concentration, this is exactly where it
would go — between ``compile_events()`` and ``reset()``/simulation, never
before ``compile_events()``.

Running it
----------

Simulating through ``km`` and recording ``time``, ``s``, and ``flag``:

.. code-block:: python

   res = km.simulate(0, 10, 11, ['time', '[s]', 'flag'])
   print(res)
   km.plot_simulation_results(labels=['s'], flag_off=5)

prints, in the ``HP_2024`` environment:

.. code-block:: text

   [[  0.    100.      1.   ]
    [  1.     36.788   1.   ]
    [  2.     13.534   1.   ]
    [  3.      4.979   1.   ]
    [  4.      1.832   1.   ]
    [  5.      0.674   0.   ]
    [  6.      0.674   0.   ]
    [  7.      0.674   0.   ]
    [  8.      0.674   0.   ]
    [  9.      0.674   0.   ]
    [ 10.      0.674   0.   ]]

``flag`` is ``1`` for every row before ``t=5`` and ``0`` from ``t=5``
onward, exactly matching the event's trigger; ``s`` decays exponentially
(``100 → 36.788 → 13.534 → 4.979 → 1.832``) while ``flag=1`` drives the rate
law, then **freezes at 0.674** for every row from ``t=5`` on, since the
event assignment zeroed ``flag`` and ``s' = -k*flag*s`` becomes ``0`` for
the rest of the run.

   ``s`` decays while ``flag=1``; the event zeroes ``flag`` at ``t=5`` h
   (dashed line), after which ``s`` holds at ~0.674 g/L.

Managing pending events
-------------------------

Before compiling, the pending list can be edited:

- :meth:`~nskinetics.KineticModel.remove_event` drops one
  pending event by name (the ``name`` passed to, or auto-generated by,
  ``Event``/``FeedSpike``).
- :meth:`~nskinetics.KineticModel.clear_events` drops all
  pending events.

Both only affect ``km.events``, the list *not yet compiled* — once
``compile_events()`` has run, the events are
baked into the RoadRunner model itself and these two methods can no longer
remove them; build a fresh ``KineticModel`` (or re-load the
model) to change the compiled event set.

``Event`` also accepts optional ``delay`` (a number or model-parameter
name giving the delay between trigger and firing) and ``priority`` (a
number or parameter name; when multiple events trigger simultaneously,
higher priority fires first) — both used to sequence the coordinated
events behind :class:`~nskinetics.FeedSpike`, covered next.

three-event pattern that adds feed to hit a target concentration whenever a
species drops below a threshold — the mechanism behind fed-batch
fermentation.
